# Phase 0 Research: Build Infrastructure Baseline

**Feature**: `001-build-infrastructure` | **Date**: 2026-09-30

## R-1: How to obtain an authentic `gradle-wrapper.jar`

**Problem**: FR-001 requires the wrapper to exist; FR-009 requires it to come from the official
distribution. Neither `gradle` nor `java` is on `PATH`, so the usual `gradle wrapper` invocation
is not directly available.

**Decision**: Generate it using the official Gradle 8.9 distribution already present in the
local wrapper cache:

```
C:\Users\adaaz\.gradle\wrapper\dists\gradle-8.9-bin\90cnw93cvbtalezasaz0blq0a\gradle-8.9
```

That directory contains a `gradle-8.9-bin.zip.ok` marker, which the Gradle wrapper writes only
after it has downloaded and successfully validated the distribution from
`services.gradle.org`. It is therefore an authentic, already-verified copy of the exact version
this project pins. Running its `wrapper` task produces `gradlew`, `gradlew.bat`, and
`gradle/wrapper/gradle-wrapper.jar` as first-party build output.

**Rationale**: the artifact is generated by the official tool from the official distribution, so
no binary is copied from an unverified source. This is the only approach available that
satisfies FR-009 without network trust assumptions.

**Alternatives considered**:

| Alternative | Rejected because |
| --- | --- |
| Download `gradle-wrapper.jar` from a GitHub raw URL | A binary from a URL cannot be verified against a published checksum for this purpose, and it violates FR-009. |
| Download the Gradle 8.9 distribution zip again | Unnecessary — a validated copy is already on disk. Re-downloading adds risk and no benefit. |
| Hand-construct the jar | Not reproducible and not verifiable. |
| Ask the developer to run `gradle wrapper` from Android Studio | Viable fallback, but it makes the fix manual and non-repeatable. Held in reserve if generation fails. |

## R-2: Which JDK runs the build

**Decision**: Android Studio's bundled runtime, confirmed present:

```
C:\Program Files\Android\Android Studio\jbr   → OpenJDK 21.0.6
```

**Rationale**: Gradle 8.9 supports running on JDK 21, and Android Gradle Plugin 8.6.0 requires
JDK 17 or newer. The JDK that *runs* Gradle is independent of the project's
`sourceCompatibility`/`targetCompatibility` of 17, so using JDK 21 does not change compilation
output. This also matches the README's existing recommendation of the bundled `jbr-21`.

**Alternatives considered**: none available — no other JDK exists on this machine. This is an
environment fact, recorded as B3 in the baseline analysis, not something this feature changes.

## R-3: Preserving the pinned version (FR-002)

**Risk identified**: the Gradle `wrapper` task **rewrites** `gradle-wrapper.properties`. That
file is tracked and currently carries explanatory comments recording *why* Gradle 8.9 was chosen
(AGP 8.6.0 compatibility). A naive regeneration would silently discard that rationale and could
also add or reorder properties.

**Decision**: invoke the task with an explicit `--gradle-version 8.9`, then diff
`gradle-wrapper.properties` and restore the original comments and `distributionUrl` if the task
altered them. The post-condition to verify is that `distributionUrl` still resolves to
`gradle-8.9-bin.zip`.

**Rationale**: FR-002 forbids changing the pinned version, and Principle VIII values the
documented rationale. Losing the comment would be an unjustified drive-by change to a tracked
file (Principle X).

## R-4: Line endings and the executable bit for `gradlew`

**Problem**: `gradlew` is a POSIX shell script. Authored on Windows, it can be committed with
CRLF line endings, which makes it unrunnable on Linux and macOS. Git also tracks an executable
bit that Windows checkouts do not set by default. The spec lists non-Windows checkouts as an
edge case.

**Decision (original)**: verify `gradlew` is written with LF endings, set the executable bit via
`git update-index --chmod=+x gradlew`, and treat repository-wide line-ending normalisation as a
residual risk rather than fixing it.

**Decision (revised 2026-09-30, after evidence)**: add a `.gitattributes` scoped to the wrapper
files only.

**Why the decision changed**: staging `gradlew` produced an explicit warning from Git —
"in the working copy of 'gradlew', LF will be replaced by CRLF the next time Git touches it" —
and `git config --show-origin --get core.autocrlf` traced `core.autocrlf=true` to
`C:/Program Files/Git/etc/gitconfig`, the Git for Windows **system** config. That ships with every
Git for Windows installation, so this affects every Windows contributor, not just this machine.
The risk was therefore not residual but confirmed: without intervention, `gradlew` would be
committed and checked out with CRLF and would fail on Linux and macOS with a `bad interpreter`
error. That directly contradicts FR-001 ("a build can be started on a clean clone") for any
non-Windows clone, and the spec names this edge case explicitly.

**Scope discipline**: the `.gitattributes` is deliberately narrow — `eol=lf` for `gradlew`,
`eol=crlf` for `gradlew.bat`, and `binary` for `*.jar`. It is **not** a repository-wide text
normalisation policy, which is what the original decision rightly declined to introduce. Only the
files this feature adds are governed.

**Verified**: after adding the rules, re-staging produced no warning; `git check-attr` reports
`eol: lf` for `gradlew` and `eol: crlf` for `gradlew.bat`; the jar reports `text: unset`; and the
staged `gradlew` blob contains zero CRLF pairs. `git ls-files --stage` shows mode `100755` on
`gradlew`.

## R-5: Verifying lint

**Decision**: verification runs `:app:assembleDebug` followed by `:app:lintDebug`. Both are
provided by the Android Gradle Plugin already applied; neither requires new configuration, which
keeps the feature inside its Out of Scope boundary on static analysis.

## Residual risks

- **Network on first wrapper run**: `gradlew` downloads the pinned distribution on first use.
  On this machine it is already cached, so verification will not exercise the download path. A
  genuinely clean machine needs network access once. This is inherent to the wrapper mechanism,
  not a defect.
- ~~**`gradlew` line endings on future edits**~~: **closed** by the revised R-4 decision. The
  `.gitattributes` rule now enforces LF regardless of a contributor's `core.autocrlf`.
- **Verification depends on the Firebase configuration file**: `:app:assembleDebug` cannot
  succeed until `app/google-services.json` is in place. Until then, verification can only prove
  the wrapper executes and reaches the same `:app:processDebugGoogleServices` failure — which
  itself confirms the wrapper works.
